# TIDEMARK Evidence Model Specification

**Version:** 1.0
**Status:** execution baseline
**Date:** 2026-08-06

**Order 8 transaction reconciliation:** 2026-08-07

## 1. Purpose

This specification defines the minimum product-native evidence needed to distinguish construction refusal, `DENY`, `ALLOW`, callback veto/release, execution, replay, and authoritative reference-workflow outcomes. It implements the evidence responsibilities in [System Architecture](../architecture/SYSTEM_ARCHITECTURE_v1.0.md) without defining storage or UI technology.

Runtime identities and decision rules are owned by [Runtime Contracts](TIDEMARK_RUNTIME_CONTRACTS_SPEC_v1.0.md). Evidence required to justify execution is durably appended before the execution adapter begins; failure to append it fails closed. The read-only UI consumes only masked review projections and has no authorization authority.

## 2. Evidence principles

- Evidence is generated by the definitive runtime, not inferred from model text, missing exceptions, or spike artifacts.
- Records are append-only. Corrections append a reconciliation event; reviewed raw evidence is not overwritten.
- Protected values, credentials, prompts containing sensitive data, and raw provider output are omitted. Masked labels and non-reversible runtime fingerprints may be stored only when required for correlation.
- Policy decisions and execution outcomes are separate records. A later execution failure does not change an `ALLOW` to `DENY`.
- Evidence required to justify execution is durably appended before the execution adapter begins; failure to append it fails closed.

### 2.1 Order 8 minimal durable prerequisite

Order 8 implements a `MinimalPreExecutionEvidenceSink` before it enables the
adapter boundary. This sink is deliberately smaller than the complete
`EvidenceRecorder` and audit store scheduled for the later evidence milestone.

The minimal sink appends only:

1. a pre-execution correlation record before any prepared-capability claim,
   protected-reference consumption, or adapter invocation; and
2. a local execution-outcome record after the adapter attempt.

It returns an explicit immutable success receipt only after the complete local
record is atomically appended, flushed, and synchronized through the
operating-system durability primitive. Any partial, unsynchronized,
malformed, duplicate, or unverifiable append is a failure. A pre-execution
append failure leaves capability and reference state unchanged and invokes no
adapter.

The minimal records contain only allowlisted schema/producer metadata,
`ExecutionId`, prepared/call/decision/invocation/tool correlations, captured
policy and registry versions, adapter identity/version, the public
prepared-call integrity identifier, the fixed authorization outcome `ALLOW`
and `authorization.allow.v1` correlation, UTC time, and the existing execution
status where applicable. They contain no runtime argument value, protected
value, `ReferenceId`, runtime-private integrity metadata, secret, store handle,
raw proposal, resolution result, or snapshot.

These minimal records and receipts are prerequisite/correlation evidence, not
authorization. The pre-execution record is not an `execution.started` marker
and does not claim that the capability was consumed or the adapter was
entered. Sections 3–10 define the complete `AuditEvent` product that remains
assigned to the later evidence milestone. That milestone must extend or replace the minimal sink without weakening the fail-closed ordering: durable evidence precedes capability consumption and adapter invocation.

## 3. Common event envelope

Every `AuditEvent` contains:

| Field | Requirement |
|---|---|
| `schema_version` | `tidemark.evidence.v1`. |
| `event_id` | Globally unique, opaque. |
| `event_type` | Closed event type from section 4. |
| `occurred_at` | Runtime-supplied UTC timestamp. |
| `sequence` | Monotonic within `trace_id`. |
| `trace_id` | Correlates one demo/run trace. |
| `invocation_id` | Present when an agent/runtime invocation exists. |
| `call_id` | Present from proposal intake onward. |
| `decision_id` | Present after a decision is sealed. |
| `prepared_call_id` | Present only for ALLOW/execution paths. |
| `execution_id` | Present only for an execution attempt or outcome. |
| `policy_version`, `registry_version` | Captured versions, when applicable. |
| `adapter_id`, `adapter_version` | Agent or execution adapter involved, when applicable. |
| `producer` | Runtime component identity and build version. |
| `payload` | Event-specific masked data. |
| `previous_event_digest` | Optional local chain link; mandatory for finalized publication exports. |

Unknown event types or schema versions are retained but not projected as authoritative explanations. Required missing fields make an event invalid and must surface as an evidence-integrity failure.

## 4. Closed event types

| Event type | Required meaning |
|---|---|
| `policy.installation_refused` | Authoring input did not produce a snapshot. |
| `call.intake_recorded` | Raw proposal received; payload is shape-only and masked. |
| `call.preparation_refused` | Complete evaluable call could not be constructed. |
| `decision.recorded` | Sealed `DENY` or `ALLOW` decision. |
| `callback.received` | Framework callback received a pending call. |
| `callback.vetoed` | Adapter returned a deterministic framework veto. |
| `callback.released` | Adapter released exactly one prepared call to execution. |
| `callback.tool_entered` | Registered tool body was entered. |
| `execution.refused` | Invalid, tampered, or adapter-mismatched prepared call was rejected before execution start. |
| `execution.started` | Execution gate accepted a prepared call. |
| `execution.completed` | Adapter returned a confirmed success. |
| `execution.failed` | The local adapter attempt failed or the external result was ambiguous; it does not assert that no side effect occurred. |
| `execution.replay_rejected` | Duplicate/consumed execution was prevented. |
| `payment.recorded` | Authoritative synthetic payment record was written. |
| `run.model_non_attempt` | Model produced no candidate tool call; not an enforcement success. |
| `evidence.reconciled` | Appends a correction/link without replacing raw events. |
| `evidence.export_finalized` | Records export digest, scope, and schema versions. |

## 5. Decision records

A `decision.recorded` payload contains:

- `outcome`: `DENY` or `ALLOW`;
- `stage`: `STRUCTURE`, `REPRESENTATION`, `RESOLUTION`, `BINDING`, `LIFECYCLE`, `VALUE`, or `AUTHORIZATION`;
- `primary_rule_id` and ordered `rule_results` (`PASS`, `FAIL`, `NOT_EVALUATED`);
- `tool_id`, contract version, policy version, and registry version;
- argument projections: name, role, supported type, provenance class, resolution/binding status, and masked display;
- masked reason facts containing only allowlisted scalar keys;
- `prepared_call_id` only when outcome is `ALLOW`.

`REFUSAL` is represented by `policy.installation_refused` or `call.preparation_refused`, not by `decision.recorded`. A refusal payload contains `refusal_code`, stage/location, captured versions, and masked detail.

Decision invariants:

1. One `call_id` has at most one sealed authorization decision.
2. A `DENY` has no `prepared_call_id` and no later `execution.started`.
3. An `ALLOW` has exactly one `prepared_call_id`; it may end in execution success, execution failure, or explicit non-execution/replay evidence.
4. Rule order and the primary failure match [Runtime Contracts](TIDEMARK_RUNTIME_CONTRACTS_SPEC_v1.0.md).

## 6. Callback trail

The ADK trail is a correlated audit sequence, not policy truth:

```text
callback.received
-> call.intake_recorded
-> call.preparation_refused -> callback.vetoed
or decision.recorded(DENY) -> callback.vetoed
or decision.recorded(ALLOW) -> callback.released -> callback.tool_entered
```

Each callback event includes framework name/version, callback name, framework invocation correlation, tool identity, and masked transport-shape metadata. Provider response content is excluded.

Required checks:

- `callback.vetoed` has no later `callback.tool_entered` for the call.
- `callback.released` identifies the prepared call and is followed by at most one `callback.tool_entered`.
- If no callback occurs, `run.model_non_attempt` may explain the run but cannot be presented as `DENY` or veto evidence.

## 7. Execution markers

An `ExecutionMarker` is the authoritative proof that the execution boundary was crossed. It is represented by `execution.started` and contains `execution_id`, `prepared_call_id`, `decision_id`, tool/adapter versions, attempt number, idempotency key fingerprint, and start time. It contains no protected execution payload. `execution.refused` is a pre-start gate result and is therefore not an execution marker.

Exactly one terminal local-attempt event (`execution.completed` or `execution.failed`) references a started execution when outcome persistence succeeds. `execution.completed` requires confirmed adapter success. Adapter exception, confirmed failure, timeout, interruption, or another ambiguous external result uses `execution.failed`; its payload states whether the external result was confirmed. An unconfirmed result remains externally unresolved even though the local attempt is terminal and consumed. It is never evidence that no side effect occurred and is never automatically retried. If terminal-outcome persistence itself fails, no terminal event may be claimed; the local execution result is `FAILED`, consumed state remains consumed, and the durable pre-execution record exposes the evidence gap for later reconciliation.

Evidence assertions:

| Authorization path | Execution markers | Authoritative payment records |
|---|---:|---:|
| Refusal or `DENY` | 0 | 0 |
| First expected `ALLOW` success | 1 started, 1 completed | 1 |
| Adapter failure after `ALLOW` | 1 started, 1 failed | 0 unless external evidence proves otherwise |
| Ambiguous external result after `ALLOW` | 1 started, 1 failed with unconfirmed external result | Unknown until authoritative reconciliation; never automatically retried |
| Replay | No second start | No second payment |

## 8. Payment records

`payment.recorded` is the reference workflow’s authoritative synthetic side-effect record, not a general payment schema. It contains:

- `payment_record_id`, `execution_id`, `prepared_call_id`, and non-secret idempotency key fingerprint;
- exact `amount_minor` and `currency`;
- trusted parent identifier;
- destination kind and masked destination display or non-reversible fingerprint;
- status `RECORDED` and authoritative store version;
- creation timestamp.

It must not contain a raw destination, opaque reference token, credential, prompt content, or model-authored narrative. The payment adapter may consume a runtime-only destination, but only the masked projection crosses into evidence.

One successful prepared call produces at most one payment record. A duplicate idempotency key or consumed prepared call produces `execution.replay_rejected`, not a second payment.

## 9. Audit event storage and queries

The complete evidence store interface introduced in the later evidence milestone must support append, lookup by correlation ID, ordered stream retrieval, and finalized export. It does not support mutation or deletion in the hackathon path. The Order 8 minimal sink has append and explicit receipt/failure behavior only; it has no query, projection, reconciliation, export, payment, callback, or UI surface.

Minimum review queries:

- all events for a `trace_id`, `invocation_id`, `call_id`, or `decision_id` in sequence order;
- decision plus callback and execution trail;
- all execution markers and payment records for a prepared call;
- schema/producer versions used in an export;
- integrity gaps, orphan outcomes, duplicate terminal events, and forbidden-field findings.

The read-only UI consumes a `ReviewProjection` produced from these queries. It never receives store write credentials.

## 10. Integrity, masking, and publication

- Masking profiles are runtime-owned and versioned. Unknown fields default to omission.
- Automated checks scan event payloads, logs, exports, screenshots, and UI fixtures for protected values and secret patterns.
- A finalized export records ordered event IDs, event digests, overall digest, producer/build versions, input fixture/protocol versions, and expected/actual result counts.
- Finalization occurs only after the run is complete. Any correction creates a new export version and `evidence.reconciled` link.
- Publication, screenshots, or demo deployment requires explicit human approval.

## 11. Acceptance summary

The evidence model is ready when every required scenario produces a complete, schema-valid trail; refusal, `DENY`, `ALLOW`, execution, replay, and model non-attempt are distinguishable; side-effect counts reconcile exactly; and neither stored nor projected evidence contains a protected value.
